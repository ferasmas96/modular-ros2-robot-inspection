Diagnosis
- Task 12D verified active cloud/IMU inputs, compatible QoS, valid TF, GLIM subscriptions, and initial IMU-state estimation. It did not capture debug traces proving LiDAR callback/conversion/preprocessing/CPU frame insertion/state update.
- PointCloud2 callback calls extract_raw_points(), TimeKeeper::process(), CloudPreprocessor::preprocess(), and asynchronous odometry insert_frame(). Failed extraction logs "failed to extract points from message"; preprocessing has TRACE input/output point counts.
- TimeKeeper rejects rewinding cloud stamps. Explicit all-zero relative times are not rejected. Mode A global-shutter preprocessing keeps times at zero and scan_end_time equals the frame stamp. Empty point/time arrays remain a source-level hazard.
- Preprocessing removes non-finite points and points outside configured 0.5–100 m range. It warns below 100 points; the LOOSE initializer skips a frame below 50 points and requires its configured 3-second initialization window and IMU data. The 5,760-point stream with a 10,000 target gets a sampling ratio above 0.99, so the random-grid sampler clones rather than downsamples.
- The async worker waits until newest IMU stamp reaches scan_end_time; it reports debug waits and warns if more than 10 frames queue. CPU insert_frame trace shows scan arrival at odometry. `frames updated` follows a subsequent scan's smoother estimate update. `workload=` is only a queue count.
- With mapping and extensions disabled, GLIM ROS polls estimator results but does not publish a default odometry topic or save an odometry trajectory. The normal shutdown "waiting for odometry estimation" line is not a failure signal.
- Viewer extension was not selected: its TF broadcaster publishes GLIM map->odom and odom->base_frame, which risks conflicting with Clearpath odom->base_link. `publish_imu2lidar=false` suppresses only imu->lidar.
